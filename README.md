# كاشر (Casher) — نقاط بيع ومخزون محلي

تطبيق عربي لنقاط البيع وإدارة المخزون. يعمل التطبيق في المتصفح ويخزن بيانات المخزون محلياً على الجهاز.

---

## 🛠️ البنية التقنية (Tech Stack)

- **Frontend**: React 19 + TypeScript + Vite + Tailwind CSS v3 + shadcn/ui + Lucide Icons
- **Database**: PGlite داخل المتصفح، مخزنة في IndexedDB على الجهاز الحالي
- **State Management**: TanStack Query v5 + React Hook Form + Zod
- **Typography & RTL**: Modern Standard Arabic, RTL-first layout (`dir="rtl"`), خط IBM Plex Arabic، دعم الأرقام العربية الشرقية (٠-٩) للعرض والأرقام اللاتينية للمدخلات والباركود.
- **Default Currency**: شيكل إسرائيلي جديد (ILS - ₪).

> 📷 **دعم قارئ الباركود وكاميرا الهاتف / الويب (Barcode & Camera Scanning):**
> النظام يدعم خيارين متكاملين لقراءة الباركود:
> 1. **أجهزة قارئ الباركود الفيزيائية (الماسحات الليزرية USB / Bluetooth):** تعمل تلقائياً مع تركيز فوري وسرعة إدخال عالية وإضافة مباشرة للسلة.
> 2. **كاميرا الهاتف أو الحاسوب (Camera Barcode Scanner):** مدعومة ومدمجة بالكامل عبر مكتبة `html5-qrcode` بنقرة واحدة على زر "مسح بالكاميرا"، مع تبديل الكاميرات الأمامية/الخلفية وإصدار تنبيه صوتي وتأكيد ليزري عند التقاط الكود.

> **حدود التخزين:** بيانات المبيعات والمخزون محفوظة محلياً في IndexedDB. تُفصل قاعدة البيانات المحلية لكل حساب فرعي على الجهاز، بينما يحتفظ المالك بقاعدة البيانات المحلية الحالية. لا تتحول بيانات POS إلى سجل سحابي بمجرد تسجيل الدخول أو نشر الواجهة على Vercel.

تبدأ قواعد البيانات الجديدة دون منتجات تجريبية. عند الترقية تُزال مرة واحدة المنتجات التجريبية المعروفة وحركات أرصدتها الافتتاحية فقط؛ لا تُمس المنتجات اليدوية، وتبقى سجلات المبيعات والحركات الأخرى محفوظة باسم المنتج بعد حذف ارتباطه. حذف المنتج يؤثر على قاعدة بيانات هذا المتصفح والجهاز فقط.

## 🚀 التشغيل المحلي (Local Development)

المشروع يعمل بالكامل دون الحاجة إلى Docker.

### 1. تثبيت الحزم:
```bash
npm install
```

### 2. تشغيل خادم التطوير:
```bash
npm run dev
```

### 3. بناء التطبيق للإنتاج:
```bash
npm run build
```

في وضع التطوير المحلي يمكن استخدام دخول المعاينة فقط. تشغيل بوابة الحسابات الفعلية يتطلب إعداد Supabase كما هو موضح أدناه؛ في الإنتاج لا يوجد تجاوز تجريبي للدخول.

## الحسابات وقفل الجهاز (يتطلب إعداد Supabase مستضاف)

يتطلب الدخول حسابًا وكلمة مرور ورمز أمان فريدًا لكل مستخدم. بعد أول دخول صحيح يُربط الحساب بتثبيت المتصفح، وتُرفض محاولة الدخول من تثبيت آخر إلى أن يصدر المالك رمز نقل عشوائيًا لمرة واحدة وصالحًا 30 دقيقة. استخدامه يبدل الجهاز المرتبط ويلغي صلاحية جلسات الجهاز السابق. تحفظ قاعدة البيانات تجزئات رموز الأمان والنقل فقط، مع تحديد محاولات الدخول. يمكن تشغيل ذلك على مشروع Supabase مستضاف دون Docker؛ لا يمكن فرض قيد جهاز مشترك باستخدام قاعدة IndexedDB المحلية وحدها. ربط الجهاز هنا بتثبيت المتصفح وليس بصمة عتادية، لذلك نسخ بيانات المتصفح يدويًا قد يستنسخ هويته.

**إعداد مطلوب قبل الاستخدام:** أنشئ مشروع Supabase مستضافًا، أضف `VITE_SUPABASE_URL` و`VITE_SUPABASE_PUBLISHABLE_KEY` إلى `.env.local`، ثم اربط Supabase CLI بالمشروع وشغّل `supabase db push` لرفع التهجيرات. انشر الدالتين `bootstrap-owner` و`provision-cashier` باستخدام `supabase functions deploy`. من لوحة Supabase فعّل Custom Access Token Hook وحدد `pg-functions://postgres/public/custom_access_token_hook`.

لإنشاء المالك الأول، عيّن سرًا عشوائيًا مؤقتًا باسم `BOOTSTRAP_OWNER_TOKEN` ضمن أسرار Supabase فقط، ثم استدعِ دالة `bootstrap-owner` عبر HTTPS ببيانات المالك والمنشأة ورأس `x-bootstrap-token`. تُرجع الدالة رمز الأمان مرة واحدة؛ احفظه بأمان ثم احذف سر التهيئة. بعد الدخول، يستطيع المالك إنشاء حسابات الكاشير وإصدار رموز نقل من صفحة «إدارة الحسابات». لا تضع `SUPABASE_SERVICE_ROLE_KEY` أو سر التهيئة في ملفات الواجهة أو في أي متغير `VITE_`.

من صفحة المنتجات يستطيع المالك نشر كتالوج المنتجات النشطة للحسابات التابعة في المنشأة. يشمل الكتالوج الاسم والباركود والوحدة والتصنيف والتكلفة وأسعار البيع والجملة والضريبة والحد الأدنى والصورة؛ **لا يشمل كمية المخزون أو الرصيد الافتتاحي أو المبيعات أو الأرباح أو حركات المخزون**. يستورد الحساب الفرعي المنتجات إلى قاعدة محلية منفصلة ويبدأ رصيد المنتج الجديد بصفر. تحديث الكتالوج لا يستبدل أرصدة الفرع المحلية، والحسابات الفرعية لا تنشر منتجاتها إلى المالك أو إلى بعضها. الصور المشتركة محفوظة في bucket عام لصور المنتجات فقط.

تتطلب مشاركة المنتجات إعداد Supabase الفعلي ورفع التهجيرات، بما فيها `20261010000003_shared_product_catalog.sql`. لا توجد مفاتيح مشروع فعلية في بيئة التطوير هذه، لذلك لم تُنشأ حسابات ولم يُختبر اتصال Supabase الحي، ولا تعمل المزامنة بين الأجهزة حتى يتم إعداد المشروع ورفع التهجيرات. قاعدة IndexedDB ليست مشفرة، ويمكن لمستخدم خبير على الجهاز نفسه فحص ملفات المتصفح.

## النشر على Vercel

1. ارفع المشروع إلى مستودع GitHub تملكه، ثم اختر **Add New → Project** في Vercel واستورد المستودع.
2. اترك إطار العمل **Vite** أو اختره يدوياً. استخدم `npm run build` كأمر البناء و`dist` كمجلد الإخراج.
3. أضف `VITE_SUPABASE_URL` و`VITE_SUPABASE_PUBLISHABLE_KEY` إلى متغيرات البيئة في Vercel؛ من دونهما ستظل بوابة الدخول مغلقة.
4. انشر المشروع. إعداد `vercel.json` يعيد توجيه مسارات تطبيق SPA إلى `index.html` حتى تعمل الروابط المباشرة والتحديث على `/products` و`/movements`.

بعد النشر، ستبقى بيانات كل متصفح/جهاز منفصلة ومخزنة محلياً في IndexedDB؛ لا يوفر Vercel تخزيناً مركزياً أو نسخاً احتياطية لهذه البيانات.

## النشر على GitHub Pages

المستودع يتضمن GitHub Actions workflow يبني التطبيق إلى `dist` وينشره عند الدفع إلى `main`. أضف `VITE_SUPABASE_URL` كـActions Variable و`VITE_SUPABASE_PUBLISHABLE_KEY` كـActions Secret في إعدادات المستودع ليعمل الدخول المنشور؛ من دونهما ستبقى بوابة الدخول مقفلة. استخدم **Settings → Pages → Build and deployment → Source → GitHub Actions** إذا لم يكن مصدر Pages مضبوطاً على Actions. رابط المشروع هو <https://zerooo563.github.io/casher/>.

يُبنى التطبيق لمسار المستودع `/casher/` على GitHub Pages، بينما يبقى المسار الافتراضي `/` متوافقاً مع Vercel. يعالج React Router المسارات داخل قاعدة URL الخاصة بالنشر، وينشئ الـworkflow صفحات ثابتة للمسارات الداخلية حتى تعمل عند فتحها أو تحديثها مباشرة.
